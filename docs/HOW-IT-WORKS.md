# How BetaCodex Chat stays with the BetaCodex

[Deutsche Fassung](WIE-ES-FUNKTIONIERT.md)

Lessons from building [BetaCodex Chat](https://chat.betacodex.org), for everyone in
the BetaCodex network who is building AI tools of their own. This document
describes what is in the code and, above all, why. The numbers in the table at the
end are generated from the code, and a test keeps the text current (see
[How this document stays current](#how-this-document-stays-current)).

## 1. Nothing was trained

The language model knows the BetaCodex no better than any other model. We neither
trained nor fine-tuned it. The answers stay with the BetaCodex because of three
levers anyone can rebuild without machine-learning expertise:

1. **Curated sources.** The model only sees texts that source curators imported.
   Answer quality depends directly on that selection.
2. **Search.** For every question, a few matching text excerpts are retrieved. The
   model sees only these. Whatever search misses, the model cannot use.
3. **Instructions.** The system prompt obliges the model to answer only from these
   excerpts and to back up every statement. Code then checks and fixes what the
   model still gets wrong.

This pattern is called RAG (retrieval-augmented generation). The basics are in the
[README](../README.md#wie-es-funktioniert-rag) (German). This document covers the
details that made the difference in practice.

## 2. The sources

- **Import:** URL, PDF, YouTube, audio, or pasted text (`app/extraction.py`). The
  text is split into overlapping chunks that end at sentence boundaries
  (`app/chunking.py`). Each chunk carries title, authors, date, and URL. That is
  the only reason every answer can name its source.
- **Local embeddings:** a multilingual model (`app/embeddings.py`) runs on our own
  server. Search costs nothing per request and works across languages: an English
  question finds German texts.
- **Summaries and key terms** are generated by AI on import (`app/summarization.py`),
  in German and English. Curators can overwrite them by hand. The key terms matter
  for search later on (section 3).
- **Relevance score 1–10** per source: core sources move up slightly in search,
  peripheral ones slightly down. A score of 5 changes nothing.
- **Approved websites** (`app/web_allowlist.py`, `app/web_crawler.py`): curators
  can approve whole websites or blogs, for example flipping-points.org. They are
  indexed weekly and included in every search.
- **The public source list** lives in [`docs/sources/`](sources/SOURCES.md), also as
  JSON and without full texts.

## 3. Conversation mode: only answers with evidence

### Search

Steps per question (`app/main.py`, function `ask`):

1. **Rewrite follow-up questions.** "Tell me more" or "what about Scrum?" are
   useless as search queries. A quick model call turns them, using the conversation
   history, into a standalone query (`rewrite_followup_query` in `app/llm.py`).
   Before this, vague follow-ups sent the search completely off topic and the model
   claimed there were no sources.
2. **Vector search with headroom.** More candidates are fetched than needed, from
   the curated sources and the approved websites at once.
3. **Rerank** by similarity, weighted with the relevance score. Duplicate texts
   take only one slot.
4. **Mentioned authors.** If a known name appears in the question, each of that
   person's sources is searched as well, and their hits get an advantage. They get a
   much larger one if one of the source's key terms is also in the question. This
   came from a question about an author and one of his concepts: the right source
   lost out to long podcast transcripts by the same person on entirely different
   topics.
5. **Hybrid search.** Terms in quotation marks and known key terms of the collection
   (including inflected forms) are guaranteed an excerpt that contains them
   verbatim.

Why step 5 was needed: pure vector search captures meaning but handles rare proper
names and technical terms poorly. For "What is {key term}?", only 56 % of cases had
any excerpt containing the term at all (82 key terms, including
"Doppelmanagement", NUMMI, John Seddon). With hybrid search it was 100 % of the
sample. We measure this without model costs using `tools/retrieval_eval.py`.

### Instructions

The system prompts are in `app/llm.py` (`SYSTEM_PROMPTS`, German and English). The
key rules:

- Only information from the supplied excerpts. No training knowledge, no
  speculation.
- Every statement gets a reference `[1]`, `[2]` at the end of the sentence.
- After the answer comes a block with the **verbatim quote** for each reference. The
  code finds that quote in the original text and highlights it in the source view,
  so readers can check any statement in seconds.
- If the excerpts cover only part of the question, the model answers with that part
  and names the gap at the end. Only if nothing fits does it use a fixed refusal
  sentence.
- If someone asks for a text ("Write me a blog post …"), the answer points to
  creative mode instead of cobbling a blog post together from excerpts.

### What we learned about prompts

- **Proximity beats position.** Rules far up in the system prompt were ignored with
  long context: English questions got German answers, and the model refused too
  often even when partial answers existed. Repeating the same rule right **after**
  the question (`_LANGUAGE_REMINDERS`, `_PARTIAL_ANSWER_REMINDERS`) worked reliably.
- **Right/wrong examples** in the prompt help more than abstract rules.
- **Never rely on a prompt alone.** Wherever an error would be visible, code fixes
  it afterwards: a leading "Answer:" is removed, references at the start of a
  sentence move to its end, a refusal sentence in front of a real answer is dropped.
  The link to creative mode is built by code, not by the model.
- **Use the fixed refusal sentence as a signal.** It is counted in the question log,
  so curators can see which topics lack sources. Users see a friendly explanation
  with tips instead of the terse sentence.

## 4. Creative mode: free writing, grounded where it is about Beta

Creative mode writes blog posts, articles, workshop concepts. It is **deliberately
looser** than conversation mode, because a workshop concept also needs facilitation
know-how that no Beta source contains. The boundary is drawn like this
(`CREATIVE_SYSTEM_PROMPTS` in `app/llm.py`):

- Matching excerpts from the curated sources are retrieved for the instruction,
  with the same hybrid search as above, and passed along as "BetaCodex context".
- **Statements about the BetaCodex must be supported by that context.** For
  everything else the model may use its knowledge and web search, but must not
  invent facts, sources, or quotes.
- **Web sources are cross-checked.** At the end the model lists the web pages it
  used. Only URLs that actually came back as search results in this very call are
  shown (`app/web_search_tool.py`). Invented links drop out.
- **Beta sources are listed by the code**, not by the model: what is shown is
  exactly what was passed in as context.
- **Style:** a style guide (`app/prompts/humanizer.md`) describes typical AI
  patterns the text should avoid, such as filler phrases, lists of three, or
  "not X but Y". It is long and identical for every request, so it is stored via
  prompt caching and costs little on follow-up requests.
- **Speed:** for the first draft the model starts writing immediately and researches
  afterwards. For research-heavy requests the wait before the first word dropped
  from about 18 to 2–5 seconds. The trade-off: the opening is written without
  research.
- **Clean-up:** announcements like "I'll research …" are cut out by code on
  revisions (`clean_section_revision`).

To be honest: creative mode does not guarantee that every sentence comes from Beta
sources. It guarantees that Beta statements are backed up and web sources are real.
If you need strictly evidenced answers, use conversation mode.

## 5. Measure instead of guessing

- `tools/retrieval_eval.py` measures search hit rates without model costs. Run it
  before and after every change to search, chunking, or ranking.
- Thumbs up/down under every answer goes to the question log, together with
  anonymised first questions and refusals. There you can see which questions people
  ask and where sources are missing.
- The cost overview shows what each mode costs. Those numbers drive the choice of
  model (section 6).

## 6. Decisions and what we dropped

- **The cheap model wherever it is enough.** Answers, rewrites, and revisions run
  on the small model. Only the first creative draft, where genuinely new text is
  written, uses the larger one. We dropped a larger model for conversation mode. The
  improvements came from search and prompt.
- **Text quality over speed in creative mode.** Dropped: fewer web searches, a
  web-search switch in the UI, the small model for the first draft.
- **Thresholds fail on dense collections.** At first the approved websites were only
  searched when the curated hits were "weak". In a thematically dense collection,
  though, some hit is almost always close enough, so the fallback practically never
  kicked in. Now it always runs, and its hits compete in the ranking.
- **No voting on sources.** Which sources count more is decided by curators through
  the relevance score, not by users voting.

## 7. Build your own, or use ours

A minimum that already goes a long way:

1. Carefully selected sources, split into chunks that carry their origin.
2. A multilingual embedding model and a vector database (we use ChromaDB).
3. A strict prompt: only from excerpts, every statement with a reference and a
   verbatim quote, a fixed refusal sentence.
4. An evaluation script for search early on, before you start tuning the prompt.

After that, in this order: hybrid search for technical terms, rewriting follow-up
questions, code safety nets for prompt rules.

BetaCodex Chat can also be used directly from Claude and other MCP clients, for
evidenced answers and for writing (`app/mcp_server.py`). Access is granted by the
admins. The code is in this repository. Questions and exchange of experience are
welcome.

## How this document stays current

A test (`tests/test_how_it_works_doc.py`) compares the table above and a fingerprint
of all prompts, the style guide, the models, and the search settings with the code.
If any of these change, the test fails, and without green tests there is no
deployment. Whoever makes the change then reviews this text and the German version
and rewrites the block with `python scripts/how_it_works.py --write`. The test also
checks that every file mentioned here exists.
